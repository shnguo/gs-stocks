# 公告观察版本库：实现与验收边界

该模块保存实际观察到的源资料和解析版本，供日后复盘查询当时已经登记的内容。它还没有证明某份公告是公司同报告期的首次数值预告，也没有启动正式前瞻收益实验。

## 入口和资料流

生产侧实现位于Rust仓库mootdx-cf：核心为crates/lakehouse-sources/src/earnings_versions.rs，离线回归为earnings_versions_tests.rs，CLI为src/research_earnings_versions.rs。

登记入口research-cninfo-earnings-register接受原捕获目录、版本库目录，以及可选的复核包JSON和数值候选JSON。它先重放原始源响应和PDF，核对索引、捕获完成时间、哈希、身份及来源绑定，再登记全部源索引记录；不会先删除亏损、未知值、修正或未下载PDF的记录。重复的同一导入返回原批次收据，不生成新批次。

查询入口research-cninfo-earnings-versions接受版本库目录、带时区的UTC查询截止时间和新的输出JSON路径。它拒绝查询未来，拒绝覆盖已有输出。每个批次的源观察时钟不得晚于登记时钟；数值提取时钟必须介于两者之间。查询只使用截止时刻之前已登记的批次，因此后来补入的旧公告不会改写过去视图。

Python脚本scripts/audit_earnings_versions.py仅承担独立研究核对。它从原捕获重新核对响应、索引、PDF、文本和数值候选字节，验证登记链和查询内容，不能将任何财务或历史资格改成通过。

## 保存和版本规则

- 证券代码与公告ID共同识别源列表文件，不猜测B股对应的A股身份。
- 每次完整导入写入新的batch目录。先保存观察内容，最后写封口清单；清单绑定本批内容、上一批清单、登记时间和当时核心代码哈希。
- 同公告的新PDF、提取代码或数值候选形成新的观察版本；旧版本保留。解析器版本号之外，还保存提取代码、候选文件、复核包、PDF和文本哈希。
- 标题类型和标题报告期声明在登记时固定，未来查询不使用新规则重新分类旧批次。多个报告期、第三季度口径不清或无明确年度的标题保留未知。
- 查询保留更早同报告期、同源声明时刻和报告期不明的前序文件。关联依赖源声明日期，只是当前发现线索；没有更早匹配不能取得首次资格。
- 本地独占锁阻止协作进程同时追加。发现已有锁、半写入批次、缺失中间批次、哈希不同、符号链接或资格升级时终止，不自动清理、重试或覆盖。

本实现使用本地文件系统和哈希链，没有外部签名或见证。若整个尾部被删除，仅凭剩余链无法发现；正式注册还需要独立保存并核对最新链头收据。单批32MiB、合计256MiB及4096批次只是当前有界实现限制，不足以直接承担多年每日全市场运行。

## 首轮真实归档验证

来源为已完成的7—9月、3月、4—5月、6月与10月1—12日五批捕获。合计1,958条上市证券/公告列表观察，数值附件为固定100份及近期10份。列表包含排除项，110份包含不支持的解析结果，均不能称为独立事件或合格交易。

初次event-version-registry-v1在独立核对中失败：11份固定样本的12个数值字段在JSON再次读入时产生相邻浮点值变化。最大金额差约0.0000002384元，不改变财务门槛，但不符合保留候选原值的约束。失败证据保存为version-registry-precision-failure-v1.json，旧版本库和查询均未覆盖。随后在CLI与源crate启用serde_json的float_roundtrip，并加入真实数值的登记、保存与查询回归。

修复后的event-version-registry-v2使用相同原归档重新登记，未重新采集市场资料。登记时间为本次实际时间，没有倒填。独立核对结果保存为version-registry-audit-v2.json；初次视图、后来补录后按同一截止时刻查询的视图、最终视图及登记前视图分别封存。

最终110个数值观察关联中，105个在已登记范围没有更早标题匹配，2个存在更早同报告期文件，3个存在报告期不明或同时间顺序问题。这些不是新的收益发现；两份更早文件已经在上一阶段追溯中发现，本轮将线索纳入可重放的版本结构。所有首次、历史及时性、财务验收与正式收益资格继续为false。

随后补齐两份更早预告的原PDF、6个公司范围查询及v10确数解析。仍在原v2库追加，当前version-registry-current-v4.json为13批、1,968条列表观察、1,959个唯一列表身份及118个数值观察版本。109个观察没有更早匹配，6个观察有更早文件，3个存在歧义；其中6个是原来两份后续文件在不同捕获与解析下的观察版本，不是6个独立事件。v9不支持的旧结果保留；v3、v4独立核对均证明补录和解析更新未改变旧截止时刻视图。详见earnings-first-version-followups-20261012.md。

后续执行原固定半月计划中尚未尝试的1月16—31日、2月1—15日与2月16—28日三个窗口，取得1674条完整分页索引并追加第14—16批，未下载新PDF。version-registry-current-v5.json目前为16批、3642条列表观察、3632个唯一列表身份和118个数值观察版本。其分类计数仍为109/6/3；逐一核对全部118个数值观察后，发现603813的一组报告期不明前序列表多出三份问询或延期公告，继续保留原歧义，未新增合格信号。

version-registry-audit-v5.json从原响应核对全部16批与9份查询输出；四个旧截止时刻均重新查询，并与各自原视图逐项相同。原13批共26个文件的字节保持不变。cninfo-fixed-halfmonth-followup-v1保存预先固定的范围、采集前链头、58页原始响应的绑定、登记回执和全部118个观察的比较。registry-update-audit-v2.json使用与独立审计相同的完整数值观察键；原简要比较保留，不能用证券/公告/解析器三字段代替完整观察身份。

## 尚未完成的首次数值事件验收

1. 已完成源分类的分页不等于全市场事件覆盖。1月1—15日仍有中止批次；1月下半月和2月的新成功批次只补该日期范围的当前分类索引，不能用它们认定半年预告没有更早数值信息。
2. 两份已追溯预告的本地捕获、原PDF哈希、完整页面检查与候选字段核对现已补齐，但均由同一Codex完成，不证明旧时刻可见。两家公司指定分类的日期连续查询也不构成全市场或全部数值披露覆盖。
3. 需建立公司与报告期身份、关联变更与重组口径，核对更早未知/负面版本，才可向首次事件筛选交付合格记录。
4. 同一Codex完成的100份原文参照不是独立人工验收。版本库不改变这一状态。
5. 每日正式运行器、完整执行资料、规则与环境注册及及时前瞻影子运行尚未完成。本次旧资料登记不能追认为正式前瞻开始。
